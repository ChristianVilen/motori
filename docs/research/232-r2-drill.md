# Research: Cloudflare R2 compatibility for the four storage workloads (#232)

Date: 2026-09-15. Feeds issue #232 (the hands-on R2 compatibility drill). Part of the storage map #226.

Sources are primary only: Cloudflare R2 docs (and their source in the `cloudflare/cloudflare-docs` repo), the `aws/aws-sdk-js-v3` repo and the exact `@aws-sdk/client-s3@3.1111.0` build from npm, OpenObserve docs and the `openobserve/openobserve` repo at tag `v0.90.3`, the `dokku/dokku-postgres` and `dokku/docker-s3backup` repos. Where I quote a GitHub issue from another project, it is marked as an observed report, not documentation.

## 1. EU jurisdiction

**Answer.** Yes: EU buckets use `https://<ACCOUNT_ID>.eu.r2.cloudflarestorage.com`. The jurisdiction is set when the bucket is created and cannot be changed. The only documented gap is Logpush. Custom domains, lifecycle rules, bucket locks, event notifications, Workers bindings, Sippy and the `r2.dev` URL all have explicit jurisdiction support. One API token can cover EU and non-EU buckets, but each jurisdiction needs its own S3 endpoint, so one S3 client per jurisdiction.

Evidence:

- Endpoint form: "you must specify the jurisdiction in your S3 endpoint: `https://<ACCOUNT_ID>.<JURISDICTION>.r2.cloudflarestorage.com`" and "When using a jurisdiction endpoint, you will not be able to access R2 resources outside of that jurisdiction" ([Data location](https://developers.cloudflare.com/r2/reference/data-location/)). The token page lists `https://<ACCOUNT_ID>.eu.r2.cloudflarestorage.com` for EU and warns: "Jurisdictional buckets can only be accessed via the corresponding jurisdictional endpoint. Most S3 clients will not let you configure multiple `endpoints`, so you'll generally have to initialize one client per jurisdiction" ([Authentication](https://developers.cloudflare.com/r2/api/tokens/)).
- Fixed at creation: "Once an R2 bucket is created, the jurisdiction cannot be changed" ([Data location](https://developers.cloudflare.com/r2/reference/data-location/)). Jurisdictions available: `eu`, `fedramp` (Enterprise only), `us`.
- Documented limitation: "The following services do not interact with R2 resources with assigned jurisdictions: Logpush" (same page). Nothing else is listed.
- Features that do support jurisdictions:
  - Workers binding: set `"jurisdiction": "<JURISDICTION>"` in the `r2_buckets` binding (same page).
  - Custom domain: the REST API to add a custom domain takes a `cf-r2-jurisdiction` header with values `default`, `eu`, `us`, `fedramp`, `fedramp-high` ([Custom domain create API](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/subresources/domains/subresources/custom/methods/create/)). Wrangler's `r2 bucket domain` commands define a `--jurisdiction` option ([workers-sdk `r2/domain.ts`](https://github.com/cloudflare/workers-sdk/blob/main/packages/wrangler/src/r2/domain.ts)).
  - Bucket locks: "If your bucket is setup with jurisdictional restrictions, you will need to pass a `cf-r2-jurisdiction` request header with that jurisdiction. For example, `cf-r2-jurisdiction: eu`" ([Bucket locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/)); Wrangler `r2 bucket lock` has `--jurisdiction` ([`r2/lock.ts`](https://github.com/cloudflare/workers-sdk/blob/main/packages/wrangler/src/r2/lock.ts)).
  - Lifecycle rules: Wrangler `r2 bucket lifecycle` has `--jurisdiction` ([`r2/lifecycle.ts`](https://github.com/cloudflare/workers-sdk/blob/main/packages/wrangler/src/r2/lifecycle.ts)); via S3 API you simply call `PutBucketLifecycleConfiguration` on the `eu` endpoint.
  - Event notifications: "Event notifications can now be configured for R2 buckets in jurisdictions (e.g., EU, FedRAMP)" (2024-10-21, [release notes](https://developers.cloudflare.com/r2/platform/release-notes/)); Wrangler [`r2/notification.ts`](https://github.com/cloudflare/workers-sdk/blob/main/packages/wrangler/src/r2/notification.ts) has `--jurisdiction`.
  - Sippy: "Sippy can now be enabled on buckets in jurisdictions" (2024-11-21, release notes); the Sippy page repeats the `cf-r2-jurisdiction: eu` header note ([Sippy](https://developers.cloudflare.com/r2/data-migration/sippy/)).
  - `r2.dev` dev URL: Wrangler [`r2/public-dev-url.ts`](https://github.com/cloudflare/workers-sdk/blob/main/packages/wrangler/src/r2/public-dev-url.ts) has `--jurisdiction`.
- One token, two jurisdictions: the token Access Policy names a bucket as `com.cloudflare.edge.r2.bucket.<ACCOUNT_ID>_<JURISDICTION>_<BUCKET_NAME>` ("For buckets not created in a specific jurisdiction this value will be `default`"), and the documented example policy lists `..._default_my-bucket` and `..._eu_my-eu-bucket` in the same token ([Authentication](https://developers.cloudflare.com/r2/api/tokens/)). So yes, one token can span jurisdictions. Our plan keeps all four buckets in EU, so this matters only for the temporary drill token.
- Metrics need the prefix too: bucket names in GraphQL are `eu_your-bucket-name` for jurisdiction buckets ([Metrics](https://developers.cloudflare.com/r2/platform/metrics-analytics/)).

Drill should test: create all four buckets from the dashboard with "Specify jurisdiction: EU" and confirm `ListBuckets` on the `eu` endpoint shows them and the plain endpoint does not.

## 2. Region and addressing

**Answer.** Use `region: "auto"`. Empty and `us-east-1` are documented aliases; `eu`, `wnam`, `hel1` are not documented as region values and should be tested, not assumed. Both path-style and virtual-hosted-style URLs appear in Cloudflare's own docs, so both are expected to work. There is no documented gotcha for either style; the EU virtual-hosted form is the one thing to verify.

Evidence:

- "When using the S3 API, the region for an R2 bucket is `auto`. For compatibility with tools that do not allow you to specify a region, an empty value and `us-east-1` will alias to the `auto` region. This also applies to the `LocationConstraint` for the `CreateBucket` API" ([S3 API compatibility](https://developers.cloudflare.com/r2/api/s3/api/)). The SDK example says `region: "auto", // Required by SDK but not used by R2` ([aws-sdk-js-v3 example](https://developers.cloudflare.com/r2/examples/aws/aws-sdk-js-v3/)).
- Location hints (`wnam`, `weur`, ...) are a `LocationConstraint` on bucket creation, not a region ([Data location](https://developers.cloudflare.com/r2/reference/data-location/)). Nothing says they are accepted as the SigV4 region.
- Path style: the S3 API page gives the bare endpoint `https://<ACCOUNT_ID>.r2.cloudflarestorage.com` and the aws CLI example uses `--endpoint-url https://<ACCOUNT_ID>.r2.cloudflarestorage.com` with `s3://bucket/key` paths ([aws CLI example](https://developers.cloudflare.com/r2/examples/aws/aws-cli/)). The `object_store` crate docs list `https://ACCOUNT_ID.r2.cloudflarestorage.com/bucket` as a recognised URL ([AmazonS3Builder](https://docs.rs/object_store/latest/object_store/aws/struct.AmazonS3Builder.html)).
- Virtual-hosted style: the presigned URLs in Cloudflare's own SDK example are `https://my-bucket.<ACCOUNT_ID>.r2.cloudflarestorage.com/dog.png` ([aws-sdk-js-v3 example](https://developers.cloudflare.com/r2/examples/aws/aws-sdk-js-v3/)), which is the SDK default when `forcePathStyle` is not set.

Drill should test: keep `forcePathStyle: true` (our current setting) and also run one `HeadObject` with `forcePathStyle: false` against the `eu` endpoint to see whether `https://motori-images.<id>.eu.r2.cloudflarestorage.com` resolves with a valid certificate. Also try `region: "hel1"` once, just to know whether R2 really ignores the value.

## 3. aws-sdk-js-v3 checksums

**Answer.** Still required as of 3.1111.0, with a catch. `requestChecksumCalculation: "WHEN_REQUIRED"` stops the CRC32 header on `PutObject` and `responseChecksumValidation: "WHEN_REQUIRED"` stops `x-amz-checksum-mode` on `GetObject`. But `DeleteObjects` and `PutBucketLifecycleConfiguration` are marked "checksum required" inside the SDK, so they send `x-amz-sdk-checksum-algorithm: CRC32` plus `x-amz-checksum-crc32` even under `WHEN_REQUIRED`. R2 does not accept CRC32 as a full-object checksum. Cloudflare's docs page does not show the setting; a PR that added it was closed without merging.

Evidence:

- The change: "3.729.0 (2025-01-15) ... This change enhances integrity protections for new SDK requests to S3. S3 SDKs now support the CRC64NVME checksum algorithm, full object checksums for multipart S3 objects, and new default integrity protections for S3 requests" ([client-s3 CHANGELOG](https://github.com/aws/aws-sdk-js-v3/blob/main/clients/client-s3/CHANGELOG.md)). The announcement says third-party services may not support it and names `WHEN_REQUIRED` as the opt-out ([issue #6810](https://github.com/aws/aws-sdk-js-v3/issues/6810)). The AWS setting names are `request_checksum_calculation` / `AWS_REQUEST_CHECKSUM_CALCULATION` and `response_checksum_validation` / `AWS_RESPONSE_CHECKSUM_VALIDATION`, default `WHEN_SUPPORTED`; the JS SDK default algorithm is CRC32 ([AWS SDK reference](https://docs.aws.amazon.com/sdkref/latest/guide/feature-dataintegrity.html)).
- What R2 supports today: the checksum table shows `CRC64NVME` FULL_OBJECT ✅ / COMPOSITE ❌ and `CRC32`, `CRC32C`, `SHA1`, `SHA256` FULL_OBJECT ❌ / COMPOSITE ✅ ([S3 API compatibility](https://developers.cloudflare.com/r2/api/s3/api/)). Release note 2025-07-03: "The CRC-64/NVME Checksum algorithm is now supported for both single and multipart objects. This also brings support for the FULL_OBJECT Checksum Type on Multipart Uploads" ([release notes](https://developers.cloudflare.com/r2/platform/release-notes/)). A single `PutObject` carries a full-object checksum, so CRC32 on `PutObject` is still the unsupported case. The same page marks `x-amz-sdk-checksum-algorithm` ❌ on `PutBucketLifecycleConfiguration` and `PutBucketCors`.
- Cloudflare's docs page still shows the client without the setting, and the docs PR "Fix aws-sdk-js-v3 code example for version 3.729.0 or later" that added `requestChecksumCalculation: 'WHEN_REQUIRED'` and `responseChecksumValidation: 'WHEN_REQUIRED'` was closed, not merged ([cloudflare-docs PR #19236](https://github.com/cloudflare/cloudflare-docs/pull/19236)). Its body quotes the error: "`501: NotImplemented: Header 'x-amz-checksum-crc32' with value (***) not implemented`". Cloudflare's .NET page does say: "`DisablePayloadSigning = true` and `DisableDefaultChecksumValidation = true` must be passed as Cloudflare R2 does not currently support the Streaming SigV4 implementation used by AWSSDK.S3" ([aws-sdk-net example](https://developers.cloudflare.com/r2/examples/aws/aws-sdk-net/)).
- What 3.1111.0 actually does (read from the published build `@aws-sdk/client-s3@3.1111.0/dist-cjs/index.js` and its `@aws-sdk/checksums` ^3.1000.28 `flexible-checksums` submodule):
  - `DEFAULT_CHECKSUM_ALGORITHM = ChecksumAlgorithm.CRC32`.
  - A checksum is added when `requestChecksumCalculation === WHEN_SUPPORTED || requestChecksumRequired`. With `WHEN_REQUIRED`, only "required" commands get one.
  - Commands wired with `requestChecksumRequired: true` include `DeleteObjectsCommand`, `PutBucketLifecycleConfigurationCommand` and `PutBucketCorsCommand`. For those the SDK sets `x-amz-sdk-checksum-algorithm: CRC32` and `x-amz-checksum-crc32`.
  - Body type decides header vs trailer: for a stream body the SDK rewrites the request to `content-encoding: aws-chunked`, `x-amz-content-sha256: STREAMING-UNSIGNED-PAYLOAD-TRAILER`, `x-amz-trailer: x-amz-checksum-crc32`; for a `Buffer` body it adds the plain `x-amz-checksum-crc32` header. Our `PutObject` uses a `Buffer`, so under `WHEN_REQUIRED` it sends no checksum header at all.
  - `GetObject` with `responseChecksumValidation: WHEN_SUPPORTED` sets `x-amz-checksum-mode: ENABLED` on the request; `WHEN_REQUIRED` leaves it out. The compat page lists no `x-amz-checksum-mode` support for `GetObject`.
- Observed reports (not docs): "`Header 'x-amz-checksum-crc32' with value 'Cu/HOQ==' not implemented`" on `PutObject`/`UploadPart` ([flysystem #1845](https://github.com/thephpleague/flysystem/issues/1845), [medusa #11068](https://github.com/medusajs/medusa/issues/11068), HTTP 501). For `DeleteObjects` against R2 with both settings on `WHEN_REQUIRED`: "It crashes with a 501 error: `NotImplemented: Header 'x-amz-sdk-checksum-algorithm' with value 'CRC32' not implemented`" ([aws-sdk-js-v3 #6819](https://github.com/aws/aws-sdk-js-v3/issues/6819), January 2025; AWS closed it as third-party). R2's own error code page lists only `InvalidDigest` (10014) and `BadDigest` (10037) for checksums, not this 501 ([Error codes](https://developers.cloudflare.com/r2/api/error-codes/)).
- AWS's documented escape hatch for `DeleteObjects`: a middleware that strips `x-amz-checksum-*` / `x-amz-sdk-checksum-*` and adds `Content-MD5` ([MD5_FALLBACK.md](https://github.com/aws/aws-sdk-js-v3/blob/main/supplemental-docs/MD5_FALLBACK.md)). R2 lists `Content-MD5` ✅ on `PutObject` and `UploadPart`; the `DeleteObjects` row does not mention checksums at all.

Drill should test, on the EU endpoint with both settings on `WHEN_REQUIRED`: `PutObject` (Buffer), `GetObject` + `transformToWebStream`, `ListObjectsV2` with `ContinuationToken`, `DeleteObject`, and `DeleteObjects` with 2 keys. If `DeleteObjects` returns 501, try (a) `ChecksumAlgorithm: "CRC64NVME"` on the command (R2 supports CRC64NVME full-object; the SDK may need the CRT add-on, unconfirmed), (b) the MD5 middleware, (c) one `DeleteObject` per key (free on R2, see Q9). Skip `PutBucketLifecycleConfiguration` from the SDK; use the dashboard or Wrangler (Q6).

## 4. API token model

**Answer.** Four levels. Object-level tokens can be scoped to a set of buckets, and one token can name two (or more) buckets, so talli's images + docs token is fine. Lifecycle and lock configuration are bucket configuration and need Admin Read & Write (or dashboard/Wrangler); an Object Read & Write token cannot do them. Jurisdiction is part of the bucket resource id in the policy; a dashboard selector is not documented. Tokens are either account tokens or user tokens, created from the R2 page.

Evidence ([Authentication](https://developers.cloudflare.com/r2/api/tokens/) unless noted):

- Permissions: "Admin Read & Write: Allows the ability to create, list, and delete buckets, edit bucket configuration, read, write, and list objects ... Admin Read only: Allows the ability to list buckets and view bucket configuration, read and list objects ... Object Read & Write: Allows the ability to read, write, and list objects in specific buckets. Object Read only: Allows the ability to read and list objects in specific buckets."
- Scoping: "If you select the Object Read and Write or Object Read permissions, you can scope your token to a set of buckets." The API example policy grants one token two bucket resources (`..._default_my-bucket` and `..._eu_my-eu-bucket`) with permission group `Workers R2 Storage Bucket Item Read`.
- Permission groups behind the levels: `Workers R2 Storage Write` (Account: "Can create, delete, and list buckets, edit bucket configuration, and read, write, and list objects"), `Workers R2 Storage Read`, `Workers R2 Storage Bucket Item Write` (Bucket: "Can read, write, and list objects in buckets"), `Workers R2 Storage Bucket Item Read`.
- `ListBuckets` from an Object-scoped token: not documented. The Object levels only speak of objects "in specific buckets". Test in drill (our apps never call `ListBuckets`, so a failure is acceptable).
- Lifecycle needs Admin: "Managing object lifecycles is a bucket-level action, and requires an API token with the `Workers R2 Storage Write` permission group" ([Object lifecycles](https://developers.cloudflare.com/r2/buckets/object-lifecycles/)). Bucket lock: "(API only) An API token with permissions to edit R2 bucket configuration", set via dashboard, Wrangler or the Cloudflare REST API ([Bucket locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/)); the S3 `PutObjectLockConfiguration` / `GetObjectLockConfiguration` APIs are unimplemented ([S3 API compatibility](https://developers.cloudflare.com/r2/api/s3/api/)).
- Object tokens and the REST API: "The Object Read & Write and Object Read only permissions are only supported by the S3-compatible API, not the Cloudflare REST API." Using one against `api.cloudflare.com` returns `{"code":10002,"message":"Unauthorized"}` (401) or, when bucket-scoped, `{"code":10000,"message":"Authentication error"}` (403) ([Troubleshooting](https://developers.cloudflare.com/r2/platform/troubleshooting/)).
- Jurisdiction on tokens: the bucket resource is `com.cloudflare.edge.r2.bucket.<ACCOUNT_ID>_<JURISDICTION>_<BUCKET_NAME>`. Whether the dashboard bucket picker shows EU buckets separately is not documented; check during the drill.
- Account vs user: "Create Account API token - These tokens are tied to the Cloudflare account itself ... Only users with the Super Administrator role can view or create them. These tokens remain valid until manually revoked. Create User API token - These tokens are tied to your individual Cloudflare user. They inherit your personal permissions and become inactive if your user is removed from the account." They are created from "R2 object storage > Account Details > Manage next to API Tokens", and "You must purchase R2 before you can generate an API token." Whether they also appear in the general account API token list is not stated; look during the drill.
- S3 credentials: "Access Key ID: The `id` of the API token. Secret Access Key: The SHA-256 hash of the API token `value`." The secret is shown once.

Recommendation for the token plan: motori and talli get Object Read & Write scoped to their buckets (talli: `motori-images` + `motori-docs`); dokku and OpenObserve get Object Read & Write on one bucket each; the drill token is Admin Read & Write so it can also set lifecycle rules, then gets revoked.

## 5. Custom domain and caching

**Answer.** A custom domain puts the bucket behind Cloudflare's CDN, and caching is on by default for common file extensions (WebP, JPG, PNG included), with a 120-minute default TTL when the object has no `Cache-Control`. To bypass for `images.motori.fi`, create a Cache Rule matching `http.host eq "images.motori.fi"` with "Bypass cache"; `cf-cache-status` then shows `DYNAMIC`. Setting `Cache-Control: no-store` on objects also works but must be done per object. The S3 endpoint is signed-request only regardless; `r2.dev` is a separate switch, off unless enabled. Custom domains work on EU buckets. Content-Type is stored as system metadata; serving it is expected but not spelled out.

Evidence:

- Caching on by default, by extension: "Domain access through a custom domain allows you to use Cloudflare Cache ... By default, only certain file types are cached. To cache all files in your bucket, you must set a Cache Everything page rule" ([Public buckets](https://developers.cloudflare.com/r2/buckets/public-buckets/)). The default extension list includes WebP, JPG, JPEG, PNG, GIF, SVG, PDF; "Cloudflare only caches based on file extension and not by MIME type"; default TTL for 200 responses without cache headers is 120 minutes; no caching when `Cache-Control` is `private`, `no-store`, `no-cache` or `max-age=0` ([Default cache behavior](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/)). R2 stores `Cache-Control` on `PutObject` ✅ ([S3 API compatibility](https://developers.cloudflare.com/r2/api/s3/api/)).
- Bypass: "When creating a cache rule, you have the option to select Bypass cache if you want matching incoming requests to not be cached", matching on "Hostname - `http.host`"; note that "the response header may return DYNAMIC rather than explicitly indicating a bypass" ([Cache rule settings](https://developers.cloudflare.com/cache/how-to/cache-rules/settings/)). Status values: `HIT`, `MISS`, `EXPIRED`, `STALE`, `BYPASS` ("the origin response was ultimately not cacheable", e.g. `no-store`), `REVALIDATED`, `UPDATING`, `DYNAMIC` ("not eligible for cache, so the request went to the origin web server without a cache lookup") ([Cache responses](https://developers.cloudflare.com/cache/concepts/cache-responses/)).
- S3 endpoint stays private: "By default, buckets are never publicly accessible and will always require explicit user permission to enable", and public access is granted per custom domain or per `r2.dev` ([Public buckets](https://developers.cloudflare.com/r2/buckets/public-buckets/)). The docs do not say in one sentence that the S3 endpoint stays signed after a domain is attached; test with an unsigned `curl https://<id>.eu.r2.cloudflarestorage.com/motori-images/<key>` and expect 401/403.
- `r2.dev` is separate: "These options can be used independently. Enabling custom domains does not require enabling `r2.dev` access." and "Disable public access to your `r2.dev` subdomain when using products like WAF or Cloudflare Access. If you do not disable public access, your bucket will remain publicly available through your `r2.dev` subdomain." Enabling it requires typing `allow`, so it is off by default (same page).
- Jurisdiction: see Q1 (custom domain API `cf-r2-jurisdiction`, Wrangler `--jurisdiction`).
- Domain rules: "The domain being used must have been added as a zone in the same account as the R2 bucket", Cloudflare-managed or partial CNAME setup (same page). `motori.fi` must therefore be a zone on the same account.
- Content-Type: `PutObject` stores `Content-Type` as system metadata ✅ ([S3 API compatibility](https://developers.cloudflare.com/r2/api/s3/api/)); "You can set the `Content-Type` (MIME type), `Content-Disposition`, `Cache-Control` and other HTTP header metadata" ([Upload objects](https://developers.cloudflare.com/r2/objects/upload-objects/)). A 2023 release note says public buckets return `Content-Encoding` for gzip objects, which shows stored metadata is served. Confirm `image/webp` with `curl -I https://images.motori.fi/<key>` in the drill.
- Edge egress via custom domain is free; "If you connect other metered services to an R2 bucket, you may be charged by those services" ([Pricing](https://developers.cloudflare.com/r2/pricing/)). Whether a cache `HIT` still counts a Class B operation is not stated; compare GraphQL counts before and after 100 cached GETs in the drill.

## 6. Bucket lock and lifecycle

**Answer.** A lock rule blocks both delete and overwrite for its retention period, applies to existing objects as well as new ones, and can be added or removed later. Retention can be a duration, a date, or indefinite; no minimum or maximum is documented (the API example uses 7 days). Lifecycle supports expire-after-days, expire-on-date, abort-multipart-after-days and transition to Infrequent Access, all with a prefix filter, via dashboard, Wrangler or the S3 `PutBucketLifecycleConfiguration` API. Lock wins over lifecycle.

Evidence, bucket locks ([Bucket locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/)):

- "Bucket locks prevent the deletion and overwriting of objects in an R2 bucket for a specified period — or indefinitely."
- "Rules apply to both new and existing objects in the bucket." So adding a lock later covers what is already there; nothing has to be re-uploaded.
- "Rules without prefix apply to all objects in the bucket." "If multiple rules apply to the same prefix or object key, the strictest (longest) retention requirement takes precedence." Up to 1,000 rules.
- Options: "Lock objects for a specific duration. For example, 90 days. Retain objects until a certain date ... Keep objects locked indefinitely." API condition shapes: `{"type": "Age", "maxAgeSeconds": 604800}` and `{"type": "Indefinite"}`. No min/max stated.
- Removal: dashboard delete, `wrangler r2 bucket lock remove <BUCKET_NAME> --id <RULE_ID>`, or PUT a configuration without the rule. Removing rules is allowed; "A bucket cannot be emptied while any bucket lock rules are configured."
- Precedence: "Bucket lock rules take precedence over lifecycle rules. For example, if a lifecycle rule attempts to delete an object at 30 days but a bucket lock rule requires it be retained for 90 days, the object will not be deleted until the 90-day requirement is met." Our plan (7-day lock, 30-day lifecycle) has the lock shorter than the lifecycle, so lifecycle deletes proceed normally.
- The exact error a blocked `DeleteObject` or overwriting `PutObject` returns is not documented; capture it in the drill.

Evidence, lifecycle ([Object lifecycles](https://developers.cloudflare.com/r2/buckets/object-lifecycles/)):

- Actions shown in the S3 example: `Expiration: { Days }`, `Expiration: { Date }`, `Transitions: [{ Days, StorageClass: "STANDARD_IA" }]`, `AbortIncompleteMultipartUpload: { DaysAfterInitiation }`, each optionally with `Filter: { Prefix }`. Set with `putBucketLifecycleConfiguration`, read with `getBucketLifecycleConfiguration`, remove with `deleteBucketLifecycle`. Tag filters and versioning rules are not shown and R2 has no versioning.
- "Objects will typically be removed from a bucket within 24 hours of the `x-amz-expiration` value." "Buckets have a default lifecycle rule to expire multipart uploads seven days after initiation." "When an object is transitioned from Standard storage to Infrequent Access storage, a Class A operation is incurred." 1,000 rule maximum.
- S3 API status: `PutBucketLifecycleConfiguration` ✅ and `GetBucketLifecycleConfiguration` ✅, but with `x-amz-sdk-checksum-algorithm` ❌ ([S3 API compatibility](https://developers.cloudflare.com/r2/api/s3/api/)). Since the JS SDK always sends that header on this command (Q3), set lifecycle rules from the dashboard or with `npx wrangler r2 bucket lifecycle add <BUCKET_NAME> --jurisdiction eu ...`.

Drill should test: put a 7-day lock on `motori-backups`, upload a key, try `DeleteObject` and `PutObject` to the same key (expect refusal, record the status and error body), then remove the rule and confirm delete works.

## 7. OpenObserve S3 settings for R2

**Answer.** There is no R2-specific provider value; `ZO_S3_PROVIDER=s3` is right (it maps to the AWS-style client, and any unknown value falls back to it). Set `ZO_S3_SERVER_URL=https://<ACCOUNT_ID>.eu.r2.cloudflarestorage.com`, `ZO_S3_REGION_NAME=auto`, keep `ZO_S3_FEATURE_FORCE_HOSTED_STYLE=false` (path style). OpenObserve's storage client (a fork of the Rust `object_store` crate) does not send CRC32 checksums, and bulk delete is off by default, so it should be R2-safe. Retention runs inside the compactor loop.

Evidence, config (all from [`src/config/src/config.rs` at v0.90.3](https://github.com/openobserve/openobserve/blob/v0.90.3/src/config/src/config.rs) unless noted):

- `ZO_S3_PROVIDER` default is `""` in source (the [environment variables page](https://openobserve.ai/docs/environment-variables/) says default `s3`, "S3 provider name, like: aws, gcs, gcp, oss, minio, swift"). `check_s3_config` fills an empty provider from the URL: `.googleapis.com` → `gcs`, `.aliyuncs.com` → `oss`, otherwise `aws`, then lowercases it.
- Client selection in [`src/infra/src/storage/remote.rs`](https://github.com/openobserve/openobserve/blob/v0.90.3/src/infra/src/storage/remote.rs): `"aws" | "s3"` → `init_aws_config`, `"azure"` → Azure, `"gcs" | "gcp"` → GCS, and `_` (anything else, e.g. `minio`) → `init_aws_config`. So `s3` and `minio` behave the same.
- `init_aws_config` builds `AmazonS3Builder::from_env()` with `.with_virtual_hosted_style_request(force_hosted_style)`, `.with_disable_bulk_delete(!cfg.s3.feature_bulk_delete)`, `.with_endpoint(server_url)` if set, `.with_region(region_name)` if set, plus the access key and secret. Client options: `with_allow_invalid_certificates(allow_invalid_certificates)`, `with_http1_only()` if `ZO_S3_FEATURE_HTTP1_ONLY`, `with_http2_only()` if `ZO_S3_FEATURE_HTTP2_ONLY`, `with_allow_http(true)`.
- `ZO_S3_FEATURE_FORCE_HOSTED_STYLE`: object_store says "false (default): Path style request is used; true: Virtual hosted style request is used" and "if `virtual_hosted_style_request` is set to true then `endpoint` should have bucket name included" ([AmazonS3Builder](https://docs.rs/object_store/latest/object_store/aws/struct.AmazonS3Builder.html)). Keep `false` with the plain account endpoint.
- `ZO_S3_REGION_NAME`: passed straight to `with_region` when non-empty. R2 wants `auto` (Q2). Our current `hel1` must change.
- `ZO_S3_FEATURE_BULK_DELETE` default `false`, so `with_disable_bulk_delete(true)`: object_store then issues "single-object `DELETE /key` requests instead of the bulk `DeleteObjects` API" (same docs page). That avoids the `DeleteObjects` checksum question from Q3 entirely, and single deletes are free on R2 (Q9).
- Checksums: the fork [`openobserve/arrow-rs-object-store` branch `openobserve-v0.13.2`](https://github.com/openobserve/arrow-rs-object-store/blob/openobserve-v0.13.2/src/aws/client.rs) (pinned in [Cargo.toml](https://github.com/openobserve/openobserve/blob/v0.90.3/Cargo.toml)) only adds `x-amz-checksum-sha256` when `checksum_algorithm` is configured to SHA256, only adds `x-amz-checksum-algorithm: SHA256` on multipart create in the same case, and OpenObserve never sets it. Bulk delete would add `Content-MD5` plus `x-amz-checksum-sha256`, but bulk delete is off. Payloads are signed SigV4 (`x-amz-content-sha256` of the body), not streaming trailers. Conditional put defaults to `ETagMatch` (`If-Match` / `If-None-Match`), which R2 lists as ✅ on `PutObject`.
- `ZO_S3_ALLOW_INVALID_CERTIFICATES`: TLS verification off; leave `false`.
- GitHub issues: searches of `openobserve/openobserve` issues for "cloudflare" and "r2 s3" returned nothing about R2 (hits were unrelated). No evidence for or against; the drill is the test.

Evidence, compaction and retention:

- `ZO_COMPACT_ENABLED` default `true`; `ZO_COMPACT_INTERVAL` default `10` seconds in the v0.90.3 source (the docs page says 60); `ZO_COMPACT_DATA_RETENTION_DAYS` default `3650`, "Minimal 3" per docs; `ZO_COMPACT_DELETE_FILES_DELAY_HOURS` default `2` in v0.90.3 (physical deletion of merged files is delayed). - The compactor job ([`src/job/compactor.rs`](https://github.com/openobserve/openobserve/blob/v0.90.3/src/job/compactor.rs)) spawns `run_generate_job` every `compact.interval` seconds, `run_merge` at interval+2, `run_retention` at interval+3 and `run_delay_deletion` at interval+4. So retention is part of compaction and runs roughly every 13 seconds with the default interval.
- `generate_jobs` in [`src/service/compact/retention.rs`](https://github.com/openobserve/openobserve/blob/v0.90.3/src/service/compact/retention.rs) returns early "if cfg.compact.data_retention_days <= 0", computes `now - data_retention_days`, and walks every org and stream; a per-stream `data_retention` setting overrides the global one.

## 8. dokku-postgres backup

**Answer.** `postgres:backup-auth <service> <aws-access-key-id> <aws-secret-access-key> [<aws-default-region>] [<aws-signature-version>] [<endpoint-url>]`; the last three are optional and stored as files. `postgres:backup` runs `dokku/s3backup:0.18.0` with a fixed set of `-e` variables and `aws s3 cp -` from stdin. The image installs Alpine's `aws-cli` v2 (unpinned). Any CLI ≥ 2.23.0 sends CRC64NVME by default, which R2 supports for single and multipart objects, so the upload will probably just work. `AWS_REQUEST_CHECKSUM_CALCULATION` is honoured by the CLI, but dokku gives no way to pass it without a custom image.

Evidence:

- Signature and defaults: `declare SERVICE="$1" AWS_ACCESS_KEY_ID="$2" AWS_SECRET_ACCESS_KEY="$3" AWS_DEFAULT_REGION="$4" AWS_SIGNATURE_VERSION="$5" ENDPOINT_URL="$6"`; only service, key id and secret are required; region, signature version and endpoint are written to `$PLUGIN_DATA_ROOT/$SERVICE/backup/<NAME>` only when non-empty ([`subcommands/backup-auth`](https://github.com/dokku/dokku-postgres/blob/master/subcommands/backup-auth), [`common-functions` `service_backup_auth`](https://github.com/dokku/dokku-postgres/blob/master/common-functions)). README example for an S3-compatible service: `dokku postgres:backup-auth lollipop MINIO_ACCESS_KEY_ID MINIO_SECRET_ACCESS_KEY us-east-1 s3v4 https://YOURMINIOSERVICE` ([README](https://github.com/dokku/dokku-postgres/blob/master/README.md)).
- The run (`service_backup` in `common-functions`): `docker container run --rm -e AWS_ACCESS_KEY_ID=... -e AWS_SECRET_ACCESS_KEY=... -e BUCKET_NAME=<bucket> -e BACKUP_NAME=postgres-<service> -v <tmpdir>:/backup [-e AWS_DEFAULT_REGION=...] [-e AWS_SIGNATURE_VERSION=...] [-e ENDPOINT_URL=...] [-e ENCRYPTION_KEY=...] [-e ENCRYPT_WITH_PUBLIC_KEY_ID=...] "$PLUGIN_S3BACKUP_IMAGE"`. With `--use-iam` the two key variables are omitted. The dump is written first with `service_export "$SERVICE" > "${BACKUP_TMPDIR}/export"`. The image is `PLUGIN_S3BACKUP_IMAGE=${PLUGIN_S3BACKUP_IMAGE:=dokku/s3backup:0.18.0}` ([`config`](https://github.com/dokku/dokku-postgres/blob/master/config)), so it can be overridden by environment.
- Inside the image ([`backup.sh`](https://github.com/dokku/docker-s3backup/blob/main/backup.sh)): `ENDPOINT_URL_PARAMETER="--endpoint-url=$ENDPOINT_URL"`; `aws configure set default.s3.signature_version "$AWS_SIGNATURE_VERSION"` when set; `tar --create --gzip --file - "backup/"` (so the archive contains `backup/export`); encryption `gpg --batch --no-tty --quiet --symmetric --cipher-algo AES256 --passphrase "$ENCRYPTION_KEY"`; upload `aws $ENDPOINT_URL_PARAMETER s3 cp - "s3://$BUCKET_NAME/$BACKUP_NAME-$TIMESTAMP.tgz.gpg"` with `TIMESTAMP=$(date -u "+%Y-%m-%d-%H-%M-%S")`. Optional `S3_STORAGE_CLASS` is not passed by dokku.
- aws CLI version: the Dockerfile at tag 0.18.0 is `FROM alpine:3.20.3` + `apk --no-cache add ... aws-cli ...` ([Dockerfile @0.18.0](https://github.com/dokku/docker-s3backup/blob/0.18.0/Dockerfile)); `main` is `alpine:3.24.1`, whose `aws-cli` package is 2.34.63 ([Alpine package](https://pkgs.alpinelinux.org/package/v3.24/community/x86_64/aws-cli)). The exact version baked into `dokku/s3backup:0.18.0` is unconfirmed; run `docker run --rm dokku/s3backup:0.18.0 aws --version` in the drill.
- CLI 2.23.0 (2025-01-15): "S3 client behavior is updated to always calculate CRC64NVME checksum by default for operations that support it, such as PutObject or UploadPart, or require it, such as DeleteObjects. Checksum behavior can be configured using the `when_supported` and `when_required` options - in the shared AWS config file using `request_checksum_calculation` and as an env variable using `AWS_REQUEST_CHECKSUM_CALCULATION`. Note: AWS CLI will no longer automatically compute and populate the Content-MD5 header" ([aws-cli CHANGELOG](https://github.com/aws/aws-cli/blob/v2/CHANGELOG.rst)). The AWS reference confirms the env var and `when_required` value ([SDK reference](https://docs.aws.amazon.com/sdkref/latest/guide/feature-dataintegrity.html)).
- R2 accepts CRC64NVME full-object checksums for single and multipart uploads since 2025-07-03 (Q3). `aws s3 cp -` streams stdin, so large dumps become multipart uploads; that path is the one to verify.

Drill should test: `dokku postgres:backup-auth motori <key> <secret> auto s3v4 https://<ACCOUNT_ID>.eu.r2.cloudflarestorage.com`, then `dokku postgres:backup motori motori-backups`, then download, `gpg --decrypt`, `tar -tzf` and check for `backup/export`. If the CLI fails on a checksum header, the fallback is a custom image (set `PLUGIN_S3BACKUP_IMAGE`) that sets `AWS_REQUEST_CHECKSUM_CALCULATION=when_required`, since `service_backup` passes no other variables through.

## 9. Payment method and metrics

**Answer.** R2 must be "purchased" (an R2 subscription added through a checkout flow) before buckets or tokens can be created, even though usage inside the free tier costs nothing; the docs do not say in plain words that a card is mandatory, but usage-based billing is preauthorised against a payment method, so expect to add one. Per-bucket operation counts are on the bucket's Metrics tab and in GraphQL via `r2OperationsAdaptiveGroups` (needs an Account Analytics Read token). `PutObject`, `ListObjects`, `CopyObject`, `CreateMultipartUpload` are Class A; `GetObject`, `HeadObject` are Class B; `DeleteObject` is free. `DeleteObjects` is not listed.

Evidence:

- "You need a Cloudflare account with an R2 subscription. If you do not have one: ... Complete the checkout flow to add an R2 subscription to your account. R2 is free to get started with included free monthly usage. You are billed for your usage on a monthly basis" ([Get started](https://developers.cloudflare.com/r2/get-started/)). "You must purchase R2 before you can generate an API token" ([Authentication](https://developers.cloudflare.com/r2/api/tokens/)). "For services subject to usage-based billing, Cloudflare may preauthorize your credit card at any point in a billing period ... In the case of R2, you will not be able to access your R2 buckets and requests will return errors, but your data will remain secure ... If you do not update your payment method within 30 days, the data related to any usage-based billing service(s) may be deleted" ([Billing policy](https://developers.cloudflare.com/billing/understand/billing-policy/)). Community threads on the card requirement exist but could not be fetched (HTTP 403), so they are not cited.
- Dashboard: "R2 object storage > select your bucket > Metrics tab", default window last 24 hours; data retained 31 days ([Metrics](https://developers.cloudflare.com/r2/platform/metrics-analytics/)).
- GraphQL: datasets `r2OperationsAdaptiveGroups` (fields `actionType`, `actionStatus` = `success` / `userError` / `internalError`, `bucketName`, `objectName`, `responseStatusCode`, `datetime`) and `r2StorageAdaptiveGroups` (`bucketName`, `payloadSize`, `metadataSize`, `objectCount`, `uploadCount`, `datetime`). "These datasets require an `accountTag` filter with your Cloudflare account ID." EU buckets are queried as `eu_<bucket>`. Example from the page:

  ```graphql
  query R2VolumeExample($accountTag: string!, $startDate: Time, $endDate: Time, $bucketName: string) {
    viewer { accounts(filter: { accountTag: $accountTag }) {
      r2OperationsAdaptiveGroups(limit: 10000,
        filter: { datetime_geq: $startDate, datetime_leq: $endDate, bucketName: $bucketName }) {
        sum { requests }
        dimensions { actionType }
      } } }
  }
  ```

  Token: "select Account in the first drop-down list, Account Analytics from the second drop-down list, and Read from the third" ([GraphQL API token auth](https://developers.cloudflare.com/analytics/graphql-api/getting-started/authentication/api-token-auth/)). This is a normal Cloudflare API token, separate from the R2 S3 tokens.
- Classes ([Pricing](https://developers.cloudflare.com/r2/pricing/)): Class A: "`ListBuckets`, `PutBucket`, `ListObjects`, `PutObject`, `CopyObject`, `CompleteMultipartUpload`, `CreateMultipartUpload`, `LifecycleStorageTierTransition`, `ListMultipartUploads`, `UploadPart`, `UploadPartCopy`, `ListParts`, `PutBucketEncryption`, `PutBucketCors` and `PutBucketLifecycleConfiguration`." Class B: "`HeadBucket`, `HeadObject`, `GetObject`, `UsageSummary`, `GetBucketEncryption`, `GetBucketLocation`, `GetBucketCors` and `GetBucketLifecycleConfiguration`." Free: "`DeleteObject`, `DeleteBucket` and `AbortMultipartUpload`." `ListObjectsV2` counts under `ListObjects`. `DeleteObjects` (bulk) is not named in any class; the drill can read its `actionType` and check whether it appears in the billed sums. "You are not charged for operations when the caller does not have permission to make the request (HTTP 401)."
- Free tier: 10 GB-month storage, 1 million Class A, 10 million Class B per month, Standard storage only; usage is rounded up to the next million operations / next GB-month ([Pricing](https://developers.cloudflare.com/r2/pricing/)).
